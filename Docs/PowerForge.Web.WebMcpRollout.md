# PowerForge.Web WebMCP Rollout

Last updated: 2026-09-04

WebMCP is a progressive enhancement for browser-based agents. It lets a page
publish structured tools that reuse the page's existing user-visible behavior.
It does not replace normal navigation, accessible forms, HTTP APIs, remote MCP
servers, or the site's authorization boundary.

The API remains experimental. The current Community Group draft is not a W3C
standard, Chrome exposes it through local testing and an origin trial, and an
agent must visit a page before it can discover that page's tools. PowerForge
therefore treats WebMCP as a verified optional capability, not a default feature
flag for every site.

Primary references:

- <https://webmachinelearning.github.io/webmcp/>
- <https://developer.chrome.com/docs/ai/webmcp>
- <https://openai.com/webmcp-challenge/>

## Rollout Phases

### Phase 0: Standard and ownership boundary

Complete.

- Use the current imperative `document.modelContext` API.
- Keep reusable registration, validation, and generated assets in
  PowerForge.Web.
- Keep the normal human interface functional when WebMCP is unavailable.
- Do not advertise a tool from configuration alone.

### Phase 1: Reusable public site search

Complete in the engine and deployed on the Evotec website.

- `site-search` is read-only and bounded.
- The runtime uses the generated same-origin search index.
- Tool output is capped at 1,500 characters, with three results by default and
  five at most.
- Generic index generation and loading are capped at 8 MiB decoded and 5,000
  entries; the manifest records source/emitted counts and truncation.
- Search indexes exclude presentation/runtime front matter, retain explicit
  search aliases and keywords, and publish byte/hash evidence in the manifest.
- Route, index, runtime integrity, tool name, and description are verified.
- `agents.json` reports WebMCP only after rendered-artifact verification passes.
- A theme can bind its existing search implementation instead of maintaining a
  second ranking engine.
- A theme whose visible search cannot reliably react to a synthetic input event
  can predeclare `renderVisibleResults(response, context)` and render the
  runtime's already-normalized, bounded results without loading a second index.

### Phase 2: Public documentation portfolio

Roll out the existing `site-search` tool only to established public sites that
already provide all of the following:

- a useful public search corpus;
- a visible `/search/` experience;
- agent-readiness generation and strict verification;
- a deployment workflow pinned to a PowerForge commit that contains WebMCP;
- a live HTTPS origin whose headers do not disable origin isolation or the
  `tools` permissions policy.

The first cohort is OfficeIMO, HtmlForgeX, IntelligenceX, CodeGlyphX, and
TestimoX. Each site owns its description and visible search UX. PowerForge owns
the tool implementation and readiness proof.

Do not enable WebMCP merely because a site is generated by PowerForge. Hold
marketing-only sites without a useful search task, authenticated control
surfaces, unpublished sites, and hosts that do not currently resolve.

### Phase 3: Product and authenticated tools

Definition is required per product before implementation. The first bounded
pilots are:

- OfficeIMO browser-local conversion, attached only to the existing converter
  UI and its existing in-browser document services. The tool may operate only
  on a file already selected in the visible page and must leave the result,
  warnings, and download action visible. Document bytes stay in the browser.
- DomainDetective public DNS queries, attached only to the existing raw-query
  playground and its current DNS engine. Inputs are a normalized public domain
  name and an allowlisted record type; the bounded response is untrusted remote
  data and must also render in the playground.

SyncSE remains outside this phase: its public site has no concrete safe workflow
that benefits from a page tool. Authenticated synchronization, licensing,
administration, support submission, and deletion remain disabled.

Phase 3 starts only when a product has a concrete task inventory and every tool
maps to existing application behavior. Generic business logic still belongs in
the product's reusable core. The WebMCP callback is a thin browser adapter.

## Tool Eligibility

Use this decision table before adding a tool:

| Surface | Default decision | Reason |
| --- | --- | --- |
| Public docs/search | Read-only tool is appropriate | The data is already public and the visible task is deterministic. |
| Public calculator/playground | Consider read-only or local-compute tools | Useful when execution is bounded and the same result is visible to the user. |
| Support/contact form | Define first | Personal data, submission intent, spam controls, and confirmation need an explicit contract. |
| Authenticated product UI | Define first | Existing identity, authorization, tenancy, and audit rules must remain authoritative. |
| Billing, licensing, tenant administration, deletion | Off by default | Consequential actions need product-specific confirmation, idempotency, and recovery semantics. |
| Unpublished or unresolved host | Off | There is no live surface to verify or deliver to users. |

## Phase 3 Safety Contract

Every non-search tool must have all of these before it can be enabled:

1. A normal user-visible control that performs the same task.
2. A narrowly scoped input schema with explicit length and count limits.
3. Existing authentication and authorization checks inside the called product
   operation, not only in the page or callback.
4. Correct WebMCP annotations. Read operations declare `readOnlyHint`; results
   containing page, user, uploaded, or remote content declare
   `untrustedContentHint`.
5. Explicit user confirmation for a consequential transition. Do not encode
   confirmation as a vague natural-language instruction in the tool description.
6. CSRF/session protection where a network mutation is involved.
7. Idempotency or a transaction identifier for retryable mutations.
8. Cancellation support and bounded execution time.
9. Privacy-bounded audit events that record the tool, outcome, actor/session,
   and transaction identity without logging secrets or document contents.
10. Tests for authorization, input bounds, cancellation, duplicate execution,
    confirmation, and visible UI synchronization.
11. A product adapter explicitly associated with the exact configured tool
    name, so sibling tools on the same page cannot satisfy each other's proof.

Until browser confirmation and declarative-form behavior settle across the
standard and implementations, state-changing tools remain product-specific and
must not be generated from arbitrary endpoint metadata.

## Deployment Acceptance

A site rollout is complete only when all of these are true:

- the consumer workflow is pinned to an exact PowerForge commit containing the
  required runtime and verifier;
- the complete site pipeline succeeds from a clean checkout;
- local agent-readiness verification passes against the rendered artifact;
- the actual `/search/` page still works without WebMCP;
- browser inspection with WebMCP enabled shows the expected tool and a real
  invocation returns bounded results while updating the visible page;
- `agent-ready exercise` passes against every deployed search page;
- each product-owned `page-tool` is invoked against the deployed page with
  representative valid and invalid inputs, and its visible result/error state
  matches the bounded callback response;
- the live deployment scan passes against the final public origin;
- no response sends `Origin-Agent-Cluster: ?0` or an effective
  `Permissions-Policy` that disables `tools` for the document;
- generated discovery metadata reports only the tools proven on that deployed
  artifact.

Source, merged configuration, a green build, and a live deployment are separate
states. Do not describe a portfolio rollout as complete until each selected
site reaches the live verification state.

## Benefits

For public documentation sites, WebMCP gives browser agents a small, typed
search operation instead of requiring them to infer search controls and scrape
result markup. That improves task reliability, preserves the visible branded
experience, reduces unnecessary page interactions, and lets the site bound the
inputs and returned data.

For product applications, the longer-term benefit is reuse of authenticated,
user-visible workflows without building a separate remote agent service. That
benefit appears only when the adapter remains thin and the product's normal
authorization, confirmation, audit, and transaction rules remain in control.
