# platyPS whole-module workflow

This packet qualifies the intact public platyPS 0.14.2 package through the canonical Hybrid CompleteModule project workflow. It requires all ten public commands, no exported aliases, 42 complete root CLR bodies and 23 private nested CLR callback members. The two alternative `ModuleNameCompleter` declarations are distinct required root bodies, identified by source line. PowerShell still owns native function registration and metadata; hosted module initialization and supported command regions remain part of the Hybrid contract.

Acquire the exact public package with the corpus runner's verified download and bounded archive helpers. Its SHA-256 is `12176941c2972577d7adbf4877ad6aebcca0920c416b46ef1131e5a5248ec59b`. Pass the unchanged expanded directory as `SourceRoot` to `Invoke-ExternalQualification.ps1`, with the selected packet and task-owned workspace/evidence paths. The packets pin all 24 package files, including the manifest, root module, two managed dependencies, localized data, template and help payload. The package and its binaries are external verification inputs; they are not redistributed in this directory.

Use `platyps-whole-module.net10.0.json` for a fresh PowerShell 7 process and `platyps-whole-module.net472.json` for a fresh Windows PowerShell 5.1 process. Cabinet cases require the existing Windows MakeCab and expand executables. This packet makes no claim about a platform without those tools.

`Invoke-PlatyPSWholeModuleProbe.ps1` accepts only `ImportPath`, `Surface`, `ScenarioRoot` and `ResultPath`. It imports the supplied manifest and requires both original managed dependencies to load from that imported module's own directory. It never resolves a missing installed dependency from the original input tree. `FixtureHelp.xml` is authored data pinned as observer support; it remains available when the common harness withdraws its staged compiler input during built and installed observation.

The observer writes only under `ScenarioRoot/platyps-observer-owned`, uses contained TEMP/CWD directories, and restores the child process context. A completed run seals a file/hash/directory inventory and the exact observer/support identities. The next surface can reuse the same ScenarioRoot only after those identities and every generated entry match. Unknown, changed, linked, unsealed or still-open content stops the reset and is preserved. Other content in ScenarioRoot is untouched.

`platyps-whole-module.scenarios.json` lists all 77 scenario identities and expected outcomes. A positive scenario must succeed. Intended negative cases retain authored errors; a setup error cannot substitute for the declared error identity. The public-export mapping is checked against each scenario's `executedExports`. Six original helper/init cases are supplemented by direct inbox completion and positive/empty optional-provider completion.

`SessionBoundary.support.ps1` replaces only the module-scoped `Invoke-Command` transport. The original `MyGetCommand` and its five nested helpers execute unchanged. An unopened owned PSSession supplies parameter identity; the bounded provider validates the authored command shape and using-variable values, then projects real local command metadata into scalar descriptors. It opens no remote connection and accesses no credentials. This is offline transport-boundary proof.

`CompleterBoundary.support.ps1` creates an isolated minimal module named TabExpansionPlusPlus under the owned workspace. Its registration function forwards to the inbox Register-ArgumentCompleter cmdlet, and its New-CompletionResult function supplies the expected typed result. This executes the pinned module's real conditional declaration and callback directly and through TabExpansion2, including an unmatched prefix. It qualifies the authored optional branch against the declared provider contract; it does not qualify the external TabExpansionPlusPlus package.

Comparable observations retain ordered values, types, errors, warnings, caught failures and file effects. The specific imported-module and generated-workspace paths receive stable labels. Native CAB/ZIP container hashes remain raw evidence outside parity; expanded payload entry names, hashes and bytes remain inside parity.

`Observation.support.ps1` declares specific output schemas after repeated fresh-original runs exposed incidental differences. Get-HelpPreview output uses an explicit help-model field schema, preserving every declared semantic field, scalar/array distinction and array order; an unexpected field fails. It validates the contained temporary MAML filename and dynamic-module GUID before recording their roles. Parser error-log JSON is observed as ordered diagnostic entries with the exact Message/FilePath/Severity values; original property order and bytes remain raw. The five declared update/merge warning cases retain the exact message payload and validate the authored clock prefix against the invocation interval.

For `cab-increment-locale`, only the declared HelpInfo XML file treats its two culture/version pairs as a map. The original `MakeHelpInfoXml` enumerates an unordered Hashtable, and fresh original processes produce both sibling orders. The observation requires the exact `en-US` version increment to `1.0.0.1`, `pl-PL` version `2.0.0.0`, URI, XML namespace, UTF-8 BOM, XML scaffolding and element formatting; duplicate, extra or changed entries fail. Both orders satisfy the [official HelpInfo schema](https://learn.microsoft.com/en-us/powershell/scripting/developer/help/helpinfo-xml-schema). Raw XML bytes and hashes remain in the original evidence. Landing-page bytes, CAB/ZIP entry inventories and expanded payload hashes stay strict. Complete unprojected scenario observations remain in `rawScenarioEvidence`; no generic XML sorting, map ordering, timestamp removal or error rewriting is applied to other output.

`requiredCompiledOwnedFunctions` requires 42 complete root CLR bodies and rejects retained hosted function source, omissions, shaping fallback or rejection. `requiredCompiledNestedFunctions` separately pins each nested body's relative source path, full declaration offsets, authored name and root owner. `parentStartLine` identifies the root ledger's body line. The common harness recursively matches those offsets in `regionGraph.scriptBlocks`, then requires the mapped member to exist in the actual artifact as a private static method with nonzero IL. Nested bodies remain native PowerShell functions whose executable clauses dispatch to compiled callbacks; they are not additional root ledger entries.

`platyps-whole-module.owned-functions.json` maps all 65 authored extents and records this nested contract. The original baseline exposed two retained conditional root bodies in hosted initialization; 40 ordinary emitted roots alone do not satisfy the packet. Static nested mappings and original scenario success do not establish actual private-method emission or built/installed qualification. The 77 workflow observations are execution evidence for their declared scenarios, without per-nested invocation counts or exhaustive branch coverage. The packet makes no Strict, runtime-free, signing, publication or performance claim.
